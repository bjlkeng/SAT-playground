# Phase 1 MAX_USED_RECENTLY Rejection Summary

Bead: `SAT-playground-5b2.2.51`

## Attempt

After closing 1.14g OTFS, Beads surfaced this as the highest-priority ready
Phase 1 executable bead. The proposed change was:

```text
MAX_USED_RECENTLY: 3 -> 2
```

The intent was to reduce lbd-tiered learned-clause database bloat by making
fresh learned clauses age into the deletion candidate pool one reduce pass
earlier.

## Benchmark Rejection

Primary comparison used the same 11-instance, 300s, 16 GiB profile mode used in
this session:

```text
SAT_USE_LBD=on
SAT_LBD_UPDATE_REASONS=on
SAT_REDUCE=lbd-tiered
SAT_CLAUSE_MIN=recursive-limited
SAT_STATS_JSON=on
SAT_TRACE_FULL=on
bash tools/bench.sh -t 300 -m 16384 -d benchmarks/profiling ...
```

Baseline (`MAX_USED_RECENTLY=3`):

- Log: `log/phase1/1.14g-otfs-profile-after-gated-off`
- Solved: 10/11

Attempt (`MAX_USED_RECENTLY=2`):

This is a status swap rather than a uniform improvement. Since it regressed the
session's required profile mode and did not preserve no-regression behavior,
`tools/compare_bench.py` returned `promotion_verdict=significant_regression`
and `verdict=FAIL`. The change was rejected and reverted.

## Final State

`MAX_USED_RECENTLY` remains `3`. The bead is left open with notes explaining the
rejection. Future work can still test the knob in the narrower
`SAT_RESTART=kissat-ema` mode described by the original bead, but it should not
be mixed into the current lbd-tiered/reason-update profile without an additional
guard for `random_v355_s3`.
