# Phase 1 MAX_USED_RECENTLY Key-Mode Retry Summary

Bead: `SAT-playground-5b2.2.51`

## Question

Retry the `MAX_USED_RECENTLY: 3 -> 2` change in the bead's intended key mode,
with the change explicitly benchmarked off and on.

## Mode

Both runs used:

```text
SAT_USE_LBD=on
SAT_RESTART=kissat-ema
SAT_REDUCE=lbd-tiered
SAT_STATS_JSON=on
```

This intentionally omits the broader previous rejection's
`SAT_LBD_UPDATE_REASONS=on` and `SAT_CLAUSE_MIN=recursive-limited` settings.

## Mechanism notes

The change does what it was expected to do on several random rows:

- `random_v285_s2`: conflicts -30.7%, learned clauses final -16.0%.
- `random_v292_s4`: conflicts -48.1%, learned clauses final -5.3%.
- `REGRandom-K4`: conflicts -20.2%, propagations -22.8%.

But the gain is not robust across the full key profile:

- `Kakuro-easy-112`: conflicts +93.0%, propagations +90.4%, runtime +124.732s.
- `Sudoku-N30-12`: conflicts +5.8%, propagations +10.4%, runtime +12.453s.
- `feistel_b64_k32_r22`: conflicts +29.3%, propagations +27.7%, runtime +3.642s.
- `mp1-Nb7T46` and `random_v355_s3` remained timeouts, so the change did not unlock a solved row.

This confirms the knob is a search-trajectory tradeoff, not a safe global
improvement. It ages noisy random clauses earlier, but it also evicts clauses
that the structured/combinatorial rows need, especially Kakuro.

## Final State

`MAX_USED_RECENTLY` remains `3`.

The bead is still open. Future work should not retry plain `MAX_USED_RECENTLY=2`
as a global constant in this key mode unless it adds a guard that protects the
Kakuro/Sudoku-style rows or scopes the change to a narrower detected condition.
